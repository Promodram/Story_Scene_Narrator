When designing the architecture for this narrative engine, I chose to represent the story as a deterministic array of JSON objects rather than relying on unstructured text and vector embeddings. I rejected the standard Retrieval-Augmented Generation approach of using an embedding model to retrieve chunks of story text based on semantic similarity. The constraints are strict: Vector databases retrieve information based on semantic similarity. If you used an embedding model to search for "Kamala talks to Tomas," it might accidentally pull in a fact from Episode 6 because the words are similar, breaking the timeline. JSON approach uses hard math guaranteeing secret being revealed to the character that isn’t part of the narrative. I avoided vector databases entirely, I created a metadata-filtered, rule-based like episode_id, character, scene as parameters. This ensures that narrative boundaries are not dynamic and completely deterministic, allowing the language model to act purely as a story generator rather than a search engine. By using a simple JSON file instead, this Narrative RAG system does not guess. It uses exact rules to decide what the character is allowed to know at that exact moment.
The narrative constraint is set in the Python backend before the LLM (qwen3:4b) ever sees the prompt. In the scene request, the FastAPI backend iterates through the JSON story events and applies a rigid filter based on two variables: the requested episode boundary and the specific character's name.If both answers are yes, the fact is added to the allowed list. If not, it is completely left out. I put this check in the Python code instead of the AI prompt because language models are bad at keeping secrets if they can see them. If you give a model the whole story and tell it to ignore the end, it will often slip up and mention things the character shouldn't know yet. By blocking those facts in our own code, the AI never sees them at all, so it cannot accidentally leak future story.
To check if a scene is good, we run test scripts that save both the allowed facts and the generated text into separate files. A human reviewer then reads the story and compares it directly against the list of permitted facts. If the character talks about an event, a secret, or a future outcome that is not on that list, we know the scene failed. While this check is very good at catching direct factual mistakes, it completely misses emotional problems. Sometimes a character mainly Wren has almost no facts to remember, especially early in the story or when they are kept in the dark. When this happens, our prompt tells the AI to focus on the immediate world around them. Instead of thinking about the past, the character focuses on what they see, hear and imagine.
They react to the physical setting, the sounds in the air, and what the other person is saying in the moment. The positive side is that the story stays focused and moves forward without long, boring explanations of the past. The downside is that these scenes can sometimes feel a bit plain and descriptive.
The weakest part of my system is that a human has to create and update the JSON file by hand. Writing down every single event and keeping track of who was in the room takes a lot of time. If a person makes a small mistake and forgets to add a character to the list, the system will hide that fact even if the character should actually know it. Another weak spot is how the system controls the length and formatting of the output. Because of time constraints during the JSON setup and working with the Qwen3:4b model which has limitations in penalty and fixes the word limit as 300 for all responses. I considered implementing an ingestion pipeline using an 8B parameter model that focuses on generating the JSON structure directly from the raw story document. However, I ultimately rejected this approach because automatic extraction is too risky for this project in this short time.
